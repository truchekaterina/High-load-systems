## 1. Словарь: коротко и по-человечески

- **ВМ (виртуальная машина)** — удалённый компьютер в облаке/у учебного провайдера. У тебя есть **логин/пароль/порт SSH**, чтобы зайти в консоль.
- **SSH** — безопасный способ зайти на ВМ в текстовом терминале: выполнять команды, копировать файлы (`scp`), делать **туннель** (см. ниже).
- **Публичный SSH-ключ (`id_rsa.pub`)** — «замок», который ты кладешь на сервер в `~/.ssh/authorized_keys`, а **приватный ключ** остаётся у тебя. Тогда вход без пароля (удобно и для скриптов).
- **Docker** — изолированные контейнеры с приложениями. **docker compose** — один файл, которым поднимаешь **несколько** контейнеров (например, приложение + PostgreSQL).
- **Переменные окружения** — настройки без правки `application.properties` в git: Spring Boot умеет читать, например, `SPRING_DATASOURCE_URL` (см. [Baeldung — Spring Boot properties from environment](https://www.baeldung.com/spring-boot-properties-env-variables)). В `docker-compose.yml` их задают в блоке `environment:`.
- **Туннель SSH (`ssh -L ...`)** — твой локальный порт (например, 8080 на ноутбуке) «приклеивается» к порту **на ВМ** (где слушает приложение). В браузере открываешь `http://localhost:8080`, а трафик идёт **через SSH** на сервер. Так проверяют API/Swagger, не открывая порт 8083 в интернет.
- **Swagger UI** — веб-страница со списком REST-эндпоинтов. В проекте `zil` для LAB6 обычно подключают **springdoc-openapi**; URL часто `http://localhost:8080/swagger-ui.html` (через туннель) или `.../swagger-ui/index.html` — смотри редирект в браузере.
- **k6** — нагрузочный тест: имитирует много HTTP-запросов, меряет **время отклика** (avg, p95 и т.д.).
- **VU (virtual users)** в k6 — не «люди», а **одновременные сценарии** (параллельные циклы запросов). В задании LAB6 важно: **VUS = const** — **фиксированное** число VU, пока меняется что-то другое (у тебя — **число доступных CPU** у контейнера приложения).
- **Соотношение 5/95, 50/50, 95/5** — доля **записи (вставка)** и **чтения** в смешанной нагрузке. Например, 5/95: 5% «тяжёлых» запросов на запись, 95% — чтение (конкретные URL бери из **раздела «Дополнительно»** в методичке; в проекте часто делают POST/PUT + GET, например под `/clients` и запрос из доп. части).
- **Шаг CPU 0.5** — в `docker-compose` у сервиса `app` меняют лимит `cpus: "0.5"`, `1.0`, `1.5` … (в зависимости от того, что разрешит Docker на ВМ), каждый раз **пересобирать не обязательно**, но контейнер **перезапускают** после смены лимита.

## 2. Что в итоге должно получиться (картинка в голове)

1. Ты **заходишь на свою ВМ** по SSH, **обновляешь ОС**, настраиваешь **вход по ключу**.
2. На ВМ **стоит git**, **клонирован** твой репозиторий, **Docker** установлен, ты **залогинена в Docker Hub** (`docker login`).
3. В каталоге с проектом `**zil`** команда `**docker compose up --build -d**` поднимает **Postgres + Spring Boot** (как в репо).
4. С **своего ПК** ты открываешь **SSH-туннель** и в браузере проверяешь **Swagger** и работу API.
5. В `docker-compose.yml` **явно** прописаны **CPU/RAM** для `app` и **переменные окружения** для: URL БД, логина/пароля БД, **Tomcat max threads**, **отключения `spring.jpa.show-sql`**.
6. Ты снимаешь **зависимость: среднее время ответа от выставленного лимита CPU** при **постоянном VU** для трёх смесей (5/95, 50/50, 95/5) и **двух схем**: нагрузка **с домашнего ПК** на ВМ и **с ВМ k6** на **твою** ВМ (или на ту же, как скажет преподаватель).

## 4. Блок B. Твой публичный ключ на ВМ (удобный вход)

**Идея:** сгенерировать на **своём ПК** пару ключей (или взять существующую), содержимое `**.pub`** вставить **на ВМ** в файл `**~/.ssh/authorized_keys`**.

### 4.1. На своём Windows (у себя)

Если ключа ещё нет (PowerShell):

```powershell
ssh-keygen -t ed25519 -C "ekaterinatryuh@yandex.ru"
```

Путь по умолчанию оставь, passphrase — по желанию.

Показать **публичный** ключ:

```powershell
Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub
```

(Если у тебя старый RSA — `id_rsa.pub`, это нормально для курса.)

### 4.2. На ВМ

```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh
nano ~/.ssh/authorized_keys
```

Вставь **одной строкой** содержимое `id_*.pub`, сохрани, выйди.

```bash
chmod 600 ~/.ssh/authorized_keys
```

Проверка: **новое окно** PowerShell на ПК — вход **без пароля**:

```powershell
ssh -p 2307 hl@hlssh.zil.digital
```

**Что это значит:** теперь **ты** — это ключ; пароль с таблицы для ssh не нужен (если сервер настроен принимать ключи).

### 5.1. Установка git

На ВМ:

```bash

```

### 5.2. Отдельный ключ «для GitHub» (лучше, чем копировать личный)

На ВМ:

```bash
ssh-keygen -t ed25519 -C "gh-labs-hls" -f ~/.ssh/id_ed25519_github

```

Скопируй **.pub** в GitHub: **Settings → SSH and GPG keys → New SSH key**.

**Почему отдельный ключ на сервере:** приватник не путать с твоим домашним; если ВМ сгорит — удалить один ключ в GitHub.

### 5.3. `ssh` config на ВМ (чтобы `git@github.com` знал, какой ключ взять)

```bash
nano ~/.ssh/config
```

Пример:

```text
Host github.com
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519_github
  IdentitiesOnly yes
```

```bash
chmod 600 ~/.ssh/config
```

Проверка:

```bash
ssh -T git@github.com
```

(Должно приветствовать пользователя `truchekaterina` / имя с GitHub.)

### 5.4. Клон

## 8. Блок F. HTTP через SSH-туннель (с твоего ПК)

В **ТЗ** написано: `ssh -L 8080:localhost:8080`. В нашем Spring Boot **по умолчанию** порт **8083** (см. `zil/application.properties` → `server.port=8083`). Значит туннель должен бить **в 8083 на ВМ** (внутри ВМ `localhost:8083` — это контейнер `app` с портом 8083).

**На Windows (второй терминал, пока сессия к ВМ не закрыта — но туннель делается одной командой):**

```powershell
ssh -p 2307 -L 8080:127.0.0.1:8083 hl@hlssh.zil.digital
```

- Оставь это окно **открытым**.
- В браузере: `http://localhost:8080/` (и путь к Swagger, см. ниже).

**Смысл разбора:** `8080` — **у тебя** на ПК, `127.0.0.1:8083` — **на удалённой машине** куда туннель пересылает.Используйте:

- `http://localhost:8080/`
- `http://localhost:8080/swagger-ui/index.html`

## 10. Блок H. `docker-compose`: CPU/RAM + переменные окружения

**Что требует ТЗ (идея):**

1. **Явно** задать **лимиты CPU и памяти** для сервиса `app` (и при необходимости `deploy.resources` — помни, что на **чистом Linux** это часто работает, на **старых** compose без swarm могут отличаться нюансы; если `deploy` игнорится, преподаватель подскажет альтернативу, например `cpus:` / `mem_limit` в новом compose).
2. **Через `environment`:**
  - `SPRING_DATASOURCE_URL`  
  - `SPRING_DATASOURCE_USERNAME`  
  - `SPRING_DATASOURCE_PASSWORD`  
  - потоки Tomcat: в Spring Boot 2/3+ свойство `server.tomcat.max-threads` → в env обычно **[верхний регистр, точка → подчёркивание, дефис → подчёркивание]**: `SERVER_TOMCAT_THREADS_MAX` (см. [релевант bind](https://docs.spring.io/spring-boot/reference/features/external-config.html), уточнить точное имя в доке к твоей версии Spring Boot / Tomcat; при сомнении смотри логи при старте — Boot выводит привязанные значения).  
  - `SPRING_JPA_SHOW_SQL=false` (или `true` при отладке) — **отключает** спам SQL в логах.
3. **Почему так:** на сервере меняют настройки **без** правок файлов в репо — только `docker compose.yml` + `.env` (который **не** коммитить с секретами) или разные `environment` в CI.

**Мини-чеклист после правок:**

```bash
docker compose up -d --build
docker inspect zil-app --format '{{.HostConfig.NanoCpus}} {{.HostConfig.Memory}}'
# и смотри env внутри контейнера:
docker exec -it zil-app env | grep -E 'SPRING|SERVER_TOMCAT'
```

## 11. Блок I. k6: эксперимент LAB6 (не путать с LAB4)

**Отличия от LAB4:**

- Ось X (по смыслу): **число CPU** (лимит контейнера), **шаг 0.5**, не VU-ступени.
- VU: **постоянное** (например, всегда 20 или 30 — **одно** число на весь график внутри одной кривой).
- Три **отдельных** прогона / три графика: смеси **5/95**, **50/50**, **95/5** (вставка/чтение по **эндпоинтам из «Дополнительно»**).
- **Два сценария сети:**  
  1. k6 **на твоём ноутбуке** → `BASE_URL` на `http://127.0.0.1:8080` (туннель) или **прямой** URL, если дадут;  
  2. k6 **на ВМ k6** (порт **2311**): зайти по SSH на эту ВМ, поставить k6, направить `BASE_URL` на **внутренний/разрешённый** адрес **твоей** ВМ/приложения (как скажет курс: через внутр. сеть `10.60.x` или публично — не открывай лишнего без инструкции).

**Практический ход (упрощённо):**

1. Зафиксировать `TARGET_VUS=const` (например 25).
2. Настроить в скрипте k6 `POST_SHARE` 0.05, 0.5, 0.95 на три серии.
3. Для **каждой** смены `cpus: "0.5"`, `"1.0"`, ... перезапустить `app`, **подождать** прогрев (1–2 мин), гонку k6 2–3 мин, сохранить **summary JSON** + подпись «сколько CPU было».
4. Построить график: **ось X** — **CPU (лимит)**, **ось Y** — **avg (или p95) времени ответа** (отдельно по «write»/«read» trend-метрикам, если сценарий разделяет).

**Где хранить артефакты:** папка вроде `zil/k6/reports-lab6/`, **README** с чему соответствуют кривые, **скрин** или `png` графиков. Не проси в git большие сырые логи, если курс не требует.

**Репозиторий:** один сценарий `zil/k6/load.js` — для LAB6 задать `LAB6_CONST=1`, `DURATION`, `TARGET_VUS`, `POST_SHARE` (см. комментарий в начале `load.js`). Обёртка `run-lab6.ps1` не обязательна — достаточно команд `k6 run` на Windows или на ВМ k6.

## 13. Если что-то идёт не так


| Симптом                          | Куда смотреть                                                                          |
| -------------------------------- | -------------------------------------------------------------------------------------- |
| `Permission denied (publickey)`  | Ключ не в `authorized_keys` на **той** машине, неверный `~/.ssh/config`                |
| `connection refused` на 8080     | Туннель не запущен, или на ВМ порт **не 8083**                                         |
| Docker «no space left»           | `docker system df`, чистка старых образов                                              |
| Hibernate засыпает SQL           | `SPRING_JPA_SHOW_SQL=false` **в environment** `app`                                    |
| `deploy.resources` не меняет CPU | Версия compose / драйвер; уточнить на курсе, возможен **cgroups v2** / rootless nuance |
