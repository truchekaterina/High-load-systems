# LAB5 — Python + requests + Faker, подготовка данных перед k6 (проект `zil`)

План для **новичка**: что делать, **зачем** и **какими простыми** средствами, без «продакшен-архитектуры».

**Порт API:** `8083` (как в лабе 4). **Стек бэка:** Spring Boot, PostgreSQL, Flyway (схема + раньше — демо-данные в `V2__seed_data.sql`).

---

## 1. Что просит задание (смысл)

Нужен **скрипт на Python**, который **до** нагрузочного теста (k6) **сам** создаёт в вашем REST-сервисе много **тестовых** записей. Данные должны выглядеть **похоже на настоящие** (имена, телефоны и т.д.) — для этого в ТЗ указана библиотека **Faker**. Запросы к API — через **HTTP** из Python — библиотека **requests**.

Дополнительно:

- **Убрать** подстановку **начальных данных из БД при развёртывании** (как в примере с `spring.sql.init` в bitbucket) — у нас это не `application.properties init`, а **миграция Flyway с демо-вставками** (`V2__seed_data.sql`). **Схема** (таблицы) **остаётся** в **V1**; **вставки демо** — убрать или вынести, чтобы **источником данных перед тестом** был только Python.
- В приложении удобно сделать эндпоинт(ы) **`/clear`**, чтобы **очистить таблицу(ы)** перед заливкой скрипта (обнулить текущие данные). В ТЗ сказано «для удобства» — **минимальный** вариант: один или несколько вызовов, которые **удаляют все строки** в нужных таблицах (с учётом **внешних ключей** — порядок важен).

**Цель в двух фразах:** (1) не зависеть от жёстко прописанного SQL-сида; (2) перед k6 **очистить** и **залить** нужное **число** объектов **одной** командой Python.

## 2. Термины простым языком

| Термин | Что это |
|--------|---------|
| **REST / REST API** | Сервис отвечает по **HTTP**: адрес `http://localhost:8083/...`, методы `GET` (взять), `POST` (создать), `DELETE` (удалить) и т.д. |
| **Эндпоинт** | «Набор пути + метода». У нас, например: `POST /clients` — **создать клиента**. В задании `--endpoint` — **какой тип** объектов вы «режиме» заливаете: в примере *users* / *tasks*; у **нас** — логично **`clients`**, **`cars`**, **`rents`**. |
| **requests** | Библиотека Python: `requests.get(url)`, `requests.post(url, json={...})` — как браузер/Postman, но из кода. |
| **Faker** | Библиотека, которая **придумывает** правдоподобные строки: имя, телефон, адрес (на язык можно настроить). **Не** путать с «настоящими» людьми — это **случайные** тестовые данные. |
| **Аргументы командной строки** | Запуск: `python seed.py --count 500 --endpoint clients`. Скрипт **сам** разбирает `--count` и `--endpoint` — в Python для этого удобен **`argparse`** (стандартная библиотека) или `click` (проект учебный — **достаточно argparse**). |
| **Внешний ключ (FK)** | В таблице `rents` есть `car_id` и `client_id` — **ссылки** на строки в `cars` и `clients`. Сначала должны **существовать** машина и клиент, **потом** можно создать аренду. **Очистка:** сначала удаляют `rents`, потом `cars` и `clients` (иначе БД ругнётся). |
| **Flyway** | При старте приложения накатывает **SQL-файлы** по порядку: `V1` — **создать таблицы**, `V2` — **когда-то** вставили демо-строки. LAB5: **V1 оставить**, **данные из V2 убрать** (или пустой `V2`, если препод требует файл). |
| **initdb-логика по данным** | Всё, что **заполняет таблицы без вашего Python** при поднятии окружения. У нас — это **V2** (и **ничего** похожего в Java с `CommandLineRunner`, если вдобавок нет). |

## 3. Что у вас в проекте `zil` (привязка к коду)

Сущности и пути (уже есть):

- **Клиенты:** `GET/POST /clients`, тело JSON с полями вроде `fullName`, `driverLicense`, `phone` (как в Postman / k6).
- **Машины:** `GET/POST /cars` — `vin`, `model`, `color`, `rentalCostPerDay`, `city`, `salonName` (точные имена смотрите в `Car` и в ответе API).
- **Аренды:** `POST /rents` — нужны **`carId`**, **`clientId`**, даты, `totalCost`. Для `rents` **зависимые таблицы** — `cars` и `clients`: скрипт должен **сначала** создать (или взять существующие id) машины и клиентов, **потом** строить аренды.

Сейчас **демо-данные** сидят в **`zil/src/main/resources/db/migration/V2__seed_data.sql`**. Их **убираем** (см. шаг 6).

## 4. Самый простой путь реализации (пошагово)

### Шаг A. Среда Python (один раз)

1. Создать **виртуальное окружение** в `zil` или рядом (по желанию): `python -m venv .venv` → активировать.  
2. Установить пакеты:  
   `pip install requests faker`  
3. (Опционально) `requirements.txt` с двумя строками — **для сдачи** и воспроизводимости.

### Шаг B. Минимальные эндпоинты «очистки» в Spring

Коротко **два** подхода (выберите один):

- **Простейший путь (рекомендуется для учёбы):** один контроллер, например `DevController` или `AdminController`, с `DELETE /dev/clear` или `POST /dev/clear`, который **в одном transaction** (или по очереди в сервисе):  
  1) удалить **все** `rents`;  
  2) удалить **все** `cars`;  
  3) удалить **все** `clients`.  
  В `Service` / `Repository` — вызвать `deleteAll()` (или существующие delete по id в цикле, но **для 500+ записей** лучше `deleteAll` у репозитория). **Порядок** обязателен.

- **Альтернатива букве ТЗ «/clear»:** три пути, например `POST /clears/cars`, `POST /clears/clients`, `POST /clears/rents` — **скрипт** вызовы делает **в одном порядке** (аренды → машины → клиенты). Больше кода, зато **буквально** «clear таблицы».

**Важно:** на **проде** такие URL **не** открывают. Для лабы достаточно **комментария** в коде: «только для dev / учеба». (Защиту `spring.profiles=dev` можно не усложнять, если в ТЗ не требуют.)

### Шаг C. Скрипт `seed.py` (логика)

1. **`argparse`:**  
   - `--count` — целое число, **по умолчанию 500**.  
   - `--endpoint` — строка, **по умолчанию** что-то одно, например `clients` (согласуйте с заданием).  
   - опционально `--base-url` — по умолчанию `http://localhost:8083`.

2. **Перед** созданием: вызвать **clear** (полный **reset** **или** только нужные таблицы — см. шаг 5).

3. **Режим `clients`:** в цикле `count` раз:  
   - `Faker` → имя, уникальные `driverLicense`, `phone` (как в k6, чтобы не дублировались),  
   - `requests.post(f"{base}/clients", json={...}, timeout=10)`  
   - проверка `r.status_code == 200` (или 201, как у вас в API).

4. **Режим `cars`:** аналогично — VIN/модель/цвет/город из Faker, числа (цена) — `random` или Faker.  
5. **Режим `rents`:** **самый наглядный элементарный путь** — **сначала** создать `count` клиентов и `count` машин (или меньше, но одинаковые id хранить в **списках** в памяти), **потом** создать `count` аренд, подставляя **случайные** `carId` / `clientId` из этих списков и **валидные** даты (чтобы `end_date > start_date`). Так вы **и** «зависимые таблицы» **и** **основной** сценарий **endpoint=rents** закрываете.  
6. **Обработка ошибок:** `try/except` + печать ответа сервера при 4xx/5xx — **для отладки** достаточно.

**Запуск перед k6 (пример):**

```text
python seed.py --count 500 --endpoint clients
docker compose up -d
k6 run load.js
```

(Порядок: БД/приложение **подняты** → `seed` → k6.)

### Шаг D. Согласование с фразой «обнуление + генерация для зависимых»

- Для `--endpoint clients` — **чистим** (хотя бы `clients` **после** `rents`, если в таблице аренд есть ссылки; безопаснее **полный** `clear` из шага B).  
- Для `cars` / `rents` — **то же**; для `rents` **обязательно** генерировать **сначала** независимые сущности, **потом** аренды.

## 5. Как **убрать** init-данные и **сохранить** схему

1. Открыть `V2__seed_data.sql`. **Удалить** все `INSERT` (или **заменить** комментариями/пустой миграцией).  
2. **Не трогать** `V1__init_schema.sql` — **таблицы** остаются.  
3. Если V2 **уже применялась** на чужой базе, Flyway **не** перезапустит V2. Для **чистой** среды: **новая БД** / `docker volume rm` (по соглашению с преподом) или **новая миграция V3** `DELETE FROM ...` (учебно обычно **проще** пересоздать volume и поднять заново).  
4. Проверка: поднять приложение, **в БД пусто** (или без демо-строк), **таблицы** есть, **заполняет** Python.

**Про `application.properties` из ссылки ZIL:** в вашем `application.properties` **нет** `spring.sql.init.data-locations` — **ничего** там выключать **не** нужно; источник демо — **V2**, не Spring init.

## 7. Что **не** усложнять (учебный уровень)

- Не нужны **Celery**, **очереди**, **брокеры**.  
- **Не** обязателен **OpenAPI-генератор** клиентов.  
- **Профили** `dev` / Basic Auth на `/clear` — **по желанию** преподавателя.  
- **Идемпотентность** «можно клацнуть clear дважды» — **достаточно** `deleteAll()`.
