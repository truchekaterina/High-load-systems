# Harbor, Git, ВМ и ветки (LAB6 / LAB7 / LAB8) — пошаговый план

Документ для **Трюх Екатерина**: **куда нажимать**, **в каком окне** вводить команды, **что пушить куда**, и **как не запутаться в ветках** на прикладной ВМ, на ПК и при работе с **Harbor** (порт **2313**).

См. также: [LAB6_PLAN_RU.md](LAB6_PLAN_RU.md), [LAB8_PLAN_RU.md](LAB8_PLAN_RU.md) (раздел «На Harbor/registry»), [docker-compose.yml](../docker-compose.yml).

**Важно:** на диске у тебя в Cursor может быть **одна** ветка, а на учебных ВМ после `git clone` часто оказывается **`main`/`master`**, и **не** `lab6-vm-docker-k6` или `lab7`. Это нормально: ниже — как **проверить ветку** и **переключиться** перед `docker compose`.

## 1. Три разных «мира» (не путать)

| Куда | Что это | Зачем |
| ---- | ------ | ----- |
| **GitHub** (`truchekaterina/Labs_hls`) | Хранит **исходный код** (Java, `docker-compose.yml`, `Dockerfile`, документация) | `git push` / `git pull` **только для файлов репозитория** |
| **Harbor** `hlssh.zil.digital:2313` | **Docker-реестр**: хранит **готовые образы** (как «артефакты» в виде image) | `docker login` → `docker build` → `docker push` — выкладываешь **образ**, не исходники |
| **Прикладная ВМ** (SSH **2307**) | Linux-сервер, где `git clone`, `docker compose` | Может не совпадать с веткой на ПК: всегда смотри `git branch` **на этой ВМ** |

**Нет отдельной «консоли на ВМ Harbor»** для `docker push`. Ты **не SSH-ишь** на Harbor: это **сетевой адрес**, к которому подключается `docker` с твоего ПК или с ВМ **2307**.

### Docker Hub и Harbor в одном `docker compose`

В [docker-compose.yml](../docker-compose.yml) **два разных источника образов** — так и задумано:

| Сервис | Откуда образ | Что нужно для `docker compose pull` |
|--------|----------------|--------------------------------------|
| **postgres** | **Docker Hub** (`postgres:16-alpine` → `docker.io`) | Обычно достаточно интернета; при rate limit — `docker login` в **Hub** (PAT). Пункт ТЗ про «ключ Docker Hub» — про это. |
| **app** | **Harbor** `hlssh.zil.digital:2313/.../zil-app:lab6` | Обязательно **`docker login hlssh.zil.digital:2313`** (логин/пароль из таблицы курса). **Логин только в Hub не подставит образ app** — для app нужен именно Harbor. |

Фраза из методички вроде «если используется Harbor на hl13, Docker Hub настраивать не нужно» означает: **для выкладки и скачивания вашего приложения** достаточно Harbor; отдельно «вешать» Hub ради **app** не требуется. Hub по-прежнему может понадобиться для **публичных** базовых образов (postgres, temurin при `docker build`) или для выполнения пункта про PAT.

| ВМ | Порт SSH | Типичное назначение |
| -- | --------- | ------------------- |
| **Прикладная** (твоя «рабочая») | **2307** | Код, `docker compose`, приложение :8083 |
| **K6** | **2311** | Только **k6** (нагрузка), обычно **не** сборка/пуш образа `zil` |
| **БД** | **2312** | PostgreSQL курса, **не** push образов основного `zil` |

## 2. Куда **вводить** команды (крупно)

### 2.1. Команды `docker login`, `docker build`, `docker push`

**Где:** на машине, где установлен **Docker** (Docker Desktop на Windows **или** Docker на ВМ **2307**).

**Папка (обязательно):** каталог **`zil`**, в котором лежат **`Dockerfile`** и (для контекста сборки) весь проект. Точка в конце `docker build ... .` означает «текущая папка = `zil`».

**Пример на Windows (PowerShell):**

```powershell
cd C:\путь\к\Labs_hls\zil
docker login hlssh.zil.digital:2313
docker build -t hlssh.zil.digital:2313/truchekaterina/zil-app:lab6 .
docker push  hlssh.zil.digital:2313/truchekaterina/zil-app:lab6
```

**Пример на прикладной ВМ (bash, та же папка `zil`):**

```bash
cd ~/work/Labs_hls/zil
docker login hlssh.zil.digital:2313
docker build -t hlssh.zil.digital:2313/truchekaterina/zil-app:lab6 .
docker push  hlssh.zil.digital:2313/truchekaterina/zil-app:lab6
```

**Где **не** делаем push образа `zil` в типичном сценарии:** на ВМ **2311 (k6)** — там гоняют нагрузку, а не собирают основной сервис (если курс явно не попросит иначе).

---

### 2.2. Команды `git pull`, `git checkout`, `git status`

**Где:** в каталоге **клона** `Labs_hls` — на **ПК** и/или на **ВМ 2307** (отдельно!). Репозиторий на ПК и на ВМ — **два разных** клона, ветка может **различаться**.

---

### 2.3. Команды `docker compose pull`, `docker compose up`

**Где:** на **той** машине, где хочешь **поднять** контейнеры (почти всегда **ВМ 2307** в задании, иногда тот же ПК для отладки).

**Папка:** снова **`Labs_hls/zil`**, рядом с `docker-compose.yml`.

```bash
cd ~/work/Labs_hls/zil
docker compose pull app
docker compose up -d
```

## 3. Полный сценарий «от нуля» (логика)

### Шаг 1 — Код (Git, на ПК)

1. Сделай изменения в ветке (например `lab6-vm-docker-k6`), закоммить.
2. `git push origin lab6-vm-docker-k6` (или как называется ветка).

**Пуш в Git — только файлы**; **образ** в Harbor сам по себе **не** обновляется, пока ты не сделаешь **шаг 2**.

### Шаг 2 — Образ (Harbor, на ПК или на ВМ 2307)

1. `cd` в **`zil`**, на **той** ветке, из которой собираешь (см. раздел 6 про ветки).
2. `docker login hlssh.zil.digital:2313` (логин/пароль **из таблицы курса** для Harbor).
3. `docker build -t <полный_тег> .` — тег **должен совпадать** с `ZIL_APP_IMAGE` в compose или в `.env` (см. раздел 4).
4. `docker push <тот_же_тег>`.

### Шаг 3 — Деплой (ВМ 2307)

1. `ssh -p 2307 hl@hlssh.zil.digital`
2. `cd` в папку клона, **`git pull`**, **переключи нужную ветку** (раздел 5).
3. `cd zil` → `docker compose pull app` → `docker compose up -d`.

## 4. Тег образа, `ZIL_APP_IMAGE` и файл `.env`

В [docker-compose.yml](../docker-compose.yml) по умолчанию:

```text
ZIL_APP_IMAGE=hlssh.zil.digital:2313/truchekaterina/zil-app:lab6
```

**Части пути:**

- `hlssh.zil.digital:2313` — хост и порт **реестра** (как в таблице).
- `truchekaterina` — **проект** в Harbor (должен **существовать** в веб-интерфейсе Harbor и совпадать с тем, куда тебе выдали права; если у курса другое имя — **исправляешь только эту часть**).
- `zil-app` — имя **репозитория** образа внутри проекта.
- `lab6` — **тег** (версия); для другой лабы можешь сделать `lab7`, `lab8` — см. раздел 6.

Если **проект** в Harbor не `truchekaterina`, **не** правьcompose в git вслепую: создай в папке **`zil`** файл **`.env`** (он в [.gitignore](../../.gitignore) — **не** улетит в Git):

```env
# zil/.env — только на твоей машине / на ВМ, не коммитить
ZIL_APP_IMAGE=hlssh.zil.digital:2313/ПРАВИЛЬНЫЙ_ПРОЕКТ_ИЗ_ВЕБ_ИНТЕРФЕЙСА_HARBOR/zil-app:lab6
```

Docker Compose **подхватит** переменные из `.env` рядом с `docker-compose.yml`.

**Пароли Harbor** в **`.env` класть не обязательно** — `docker login` один раз кладёт учётные данные в `~/.docker/config.json` на той машине, где залогинилась.

## 5. «На ВМ не та ветка» — что делать

На **приложение ВМ (2307)**:

```bash
cd ~/work/Labs_hls
git status
git branch -a
```

- Если смотришь **LAB6** (Harbor, k6, compose с локальным postgres как в [docker-compose.yml](../docker-compose.yml)) — переключись на ветку, где лежат эти настройки, например:

  ```bash
  git fetch origin
  git checkout lab6-vm-docker-k6
  git pull origin lab6-vm-docker-k6
  ```

- Имя ветки возьми **из репо на GitHub** (или из [LAB6_PLAN_RU.md](LAB6_PLAN_RU.md)); если ветка называется иначе — используй **фактическое** имя.

**После смены ветки** снова зайди в `zil` и **перечитай** `docker-compose.yml`: на другой ветке структура могла отличаться (см. раздел 6).

## 6. Ветки LAB6, LAB7, LAB8 — что «вероятно» другое

Одна и та же папка `zil` **на разных ветках** может содержать **разный** `docker-compose.yml` и **разные** `application.properties`. Ниже — **ожидаемая** логика, без привязки к тому, что сейчас в каждом коммите (проверяй **своим** `git show` / файлом на ветке).

| Ветка / тема | Типичный смысл | Docker / Harbor |
| ------------- | -------------- | ---------------- |
| **LAB6** | Образ `app` из реестра, опционально **встроенный** PostgreSQL в compose, CPU/лимиты, k6 | Один образ (например `...:lab6` или `...:latest`). `docker compose pull app` + `up` |
| **LAB7** | Часто приложение смотрит в **внешнюю БД** (отдельная ВМ, порт, `hl7`, хост `hl12.zil` и т.д.) | Compose может **не** зависеть от локального `postgres` **или** держать postgres только «для IDE». **Тот же** Dockerfile часто копируется; тег образа в Harbor логично сделать **`...:lab7`**, чтобы не перетереть `lab6` в отчётах. Сборка: снова `docker build` + `push` с **новым тегом** |
| **LAB8** | Основной `zil` + **второй** микросервис ( **отдельный** репо или второй сервис в compose), образ **два** (или app + `additional`) | Пуши **два** образа в Harbor, в compose — **два** `image:` (см. [LAB8_PLAN_RU.md](LAB8_PLAN_RU.md)). **Не** путай тег/имя `zil-app` с именем репо **zil-additional-service** |

**Нужно ли «исправлять» старые ветки под Harbor?**

- **LAB6 (текущий подход):** `docker-compose` уже с `image: ${ZIL_APP_IMAGE:...}`. Достаточно **собрать/запушить** образ с совпадающим тегом.
- **LAB7 / LAB8:** если на той ветке ещё `build: context` без `image` с Harbor — для зачёта «образ из реестра» придётся **влить/перенести** правку (как в `main`/lab6) **или** на защите поднимать с той ветки, куда вы уже **вмержили** compose с `image` — уточни у преподавателя.

**Практично:** веди **чёткие теги** в Harbor: `...:lab6`, `...:lab7`, чтобы в отчётах и на ВМ не перепутать, какой образ относится к какой лабе.

## 7. Что «пушить» и что «выгружать» (шпаргалка)

| Действие | Команда / место | Что в итоге |
| -------- | --------------- | ----------- |
| Выложить **код** | `git add` / `commit` / `git push` на **GitHub** | Обновляется репо, **не** образ в Harbor |
| Выложить **образ приложения** | `docker push` на **Harbor** | Появляется/обновляется image по тегу |
| **Скачать** образ на ВМ | `docker compose pull app` (из `zil`) | Локальный кэш Docker на **этой** машине |
| **Скачать** код на ВМ | `git pull` в `Labs_hls` | Файлы соответствуют ветке |

**«Выгрузка»** с ВМ в Git обычно **не** нужна для агента: правки делают на **ПК** или в веб-редакторе, потом `git push` и на ВМ снова `git pull`. Если **на** ВМ правили — тот же `git add/commit/push` (осторожно с секретами в `.env` — он не в Git).

## 8. Настройки Docker при ошибках (Harbor, HTTPS)

Если `docker login` пишет про **сертификат** или **HTTP/HTTPS** — **по инструкции курса** (не копипаста из интернета): на Linux иногда в `/etc/docker/daemon.json` добавляют `insecure-registries` с **`"hlssh.zil.digital:2313"`**; в **Docker Desktop** (Windows) — **Settings → Docker Engine** аналогично, затем **Restart**.

## 9. SSH-туннель (напоминание, с ПК)

С ноутбука, **отдельное** окно (подключение к **2307**), приложение в контейнере на **8083**:

```powershell
ssh -p 2307 -L 8080:127.0.0.1:8083 hl@hlssh.zil.digital
```

Браузер: `http://localhost:8080/swagger-ui/index.html` (пока сессия открыта). Это **не** связано с Harbor, только с **доступом к API** с твоего ПК.

## 10. Скрипт `open-swagger.ps1` (только Windows, папка `zil`)

[open-swagger.ps1](../open-swagger.ps1) делает `docker compose pull app`, при неудаче — **локальный** `docker build` с **тем же** тегом, что в `ZIL_APP_IMAGE` по умолчанию, затем `up -d`. Удобно, когда **ещё** не пушила в Harbor: соберёт локально. Для **чистой** проверки «как на ВМ» сначала **запуши** в Harbor, потом `pull`.

## 11. Чеклист перед сдачей / демо

- [ ] На **ПК** или **2307** выполнен `docker login hlssh.zil.digital:2313` (учётка из таблицы).
- [ ] `docker build` и `docker push` с **тем же** полным тегом, что в `ZIL_APP_IMAGE` (или в `.env`).
- [ ] На **2307** в каталоге `Labs_hls`: **нужная** ветка (`git branch`), `git pull`.
- [ ] В `zil`: `docker compose pull app` → `docker compose up -d` → `docker ps` (есть `zil-app`).
- [ ] `curl` / браузер по SSH-туннелю: что-то вроде `http://127.0.0.1:8083/cars` **на ВМ** или `localhost:8080` **через туннель** с ПК.
- [ ] Пароли и **`.env` с секретами** — **не** в публичном `git commit`.

## 12. Куда смотреть, если снова запутаешься

| Вопрос | Ответ |
| ------ | ----- |
| Куда `docker push`? | В **Harbor** (адрес с `:2313`), **не** в Git. |
| Куда `git push`? | В **GitHub** — только **файлы** репозитория. |
| Нужен ли отдельный SSH на «ВМ Harbor»? | **Нет** — `docker` сам ходит на `hlssh.zil.digital:2313`. |
| Где k6? | ВМ **2311**; образ `zil` туда обычно **не** пушат. |
| Обязательна ли папка `zil` для `build`? | **Да** — `Dockerfile` в ней, контекст — `.` в конце команды. |

*Документ согласован с репозиторием по смыслу: Harbor по умолчанию, ветки — проверяй на своём `git`. Точные имена ветек и критерии зачёта — у преподавателя.*
