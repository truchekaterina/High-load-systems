## Часть 0. Зачем нам LAB9 простыми словами

**Проблема.** Под нагрузкой приложение тормозит. Внешние инструменты (k6, графики) показываут только «сколько времени занял HTTP-ответ целиком». Неясно:

- тормозит **контроллер**?
- тормозит **запрос в БД**?
- тормозит **вызов основного сервиса из additional**?
- тормозит **сборка статистики в Java на additional**?

**Что делает лабораторная.** Вы добавляете свой слой наблюдаемости:

1. **`ObservabilityService`** — программа сама записывает: «в такой категории был вызов, он длилось столько наносекунд», и хранит это за **скользящие окна времени** (например последние 10 секунд, 30 секунд и 1 минута — длительности **не зашиты в код жёстко**, а задаются в `application.properties`, чтобы методист мог сказать «поменяй окно» без пересборки логики).
2. **`@Scheduled` бин** раз в несколько секунд **выгружает в лог** агрегаты: сколько было вызовов, среднее время и т.д. Поэтому после прогона k6 вы **сохраняете лог** и прикладываете к отчёту как доказательство «что приложение считало внутри».
3. **Таймеры вручную** (`start/stop`) в нужных местах — потому что задание требует явно видеть интервалы, а не «магический» AOP один раз навсегда (хотя дальше в жизни вы можете перейти на Micrometer/Actuator; здесь учим основу).

**Итого зачем:** понять связь CPU/нагрузки с узкими местами **в коде ваших двух сервисов**, а не только «кривая k6 упала».

## Часть 3А. Если **`additional` на hl13**, а **`app` на hl07**

У многих **hl13** ещё и имя узла Harbor (**`docker login hl13.zil:8888`**). Отдельно: **контейнер `additional`** на **hl13** — это уже **служба HTTP** на **8084**, ей нужен **рабочий URL** основного приложения (**8083**) на hl07 по **внутренней сети**.

**Зачем отдельный раздел.** В одном `docker-compose` часто указано **`MAIN_SERVICE_BASE_URL=http://app:8083`**. Имя **`app`** — это контейнер **в той же** docker-сети. Если **`additional` на другой ВМ**, имени **`app`** там нет — подставьте **`http://<IP hl07 из сети курса>:8083`** (переменная окружения в compose доп. сервиса).

**Пошагово:**

1. **hl07** — поднимите **`app`** (без необходимости поднимать `additional`):  
   `docker compose --env-file registry-tags-lab8-hl7.env up -d --force-recreate app`

2. На **hl07** узнайте **внутренний IP** (часто `10.60.*.*`): `hostname -I`. Обозначьте **`HL07_IP`**.

3. На **hl13** для окружения контейнера **`additional`** задайте:  
   **`MAIN_SERVICE_BASE_URL=http://<HL07_IP>:8083`**  
   (или свой альтернативный ключ из кода добав. сервиса).

4. **С hl13** проверьте CRUD по сети:  
   `curl -sS -o /dev/null -w "%{http_code}\n" http://<HL07_IP>:8083/stats` → **`200`**.

5. На **hl13**:  
   `curl -sS -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8084/additional/stats` → **`200`**.

6. **hl11 (k6):**  
   `export BASE_URL=http://<HL13_IP>:8084` — IP **узла с добав. сервисом**, не hl07.

7. **CPU 0.5 / 1.0:** на **hl07** меняете **`APP_CPUS`**, на **hl13** — **`ADDITIONAL_CPUS`**, синхронно перед каждым кругом k6.

8. **Логи LAB9:** `docker compose logs` на hl07 только **`app`**; на hl13 только контейнер **`additional`**. Приложите к отчёту оба файла или один склеенный.

## Часть 4. Основное приложение (`zil` на ПК) — порядок «что создать и куда тыкнуть»

Дальнейшие шаги описывают **целевое состояние** кода. Если класс уже назван иначе — сохраните суть.

### Шаг 4.1. Открыть проект правильной папки

1. В Cursor / IntelliJ через **File → Open** выберите папку, где лежит **`build.gradle`** (или Maven) этого сервиса — в курсе это внутрь **`zil`**, например **`.../Labs_hls/zil`**, а не просто **`Labs_hls`**, если корень сборки там.

**Зачем:** иначе Gradle не найдёт исходники и тесты.

### Шаг 4.2. Включить планирование задач (`@Scheduled`)

1. Откройте файл **`src/main/java/rental/Application.java`**.
2. На класс **`Application`** добавьте аннотацию **`@EnableScheduling`** рядом с **`@SpringBootApplication`** (порядок не критичен).
3. Сохраните файл.

**Зачем:** Spring начнёт вызывать методы с `@Scheduled` из бинов. Без этого лабораторная «не шумит» в логах — вы решите, что сервис сломан.

### Шаг 4.3. Создать пакет и класс `ObservabilityService`

1. В дереве проекта: **`src/main/java/rental`** → правый клик → **New → Package**.
2. Имя пакета, например: **`observability`** (получится **`rental.observability`**).
3. На пакете **`observability`** → правый клик → **New → Java Class**.
4. Имя класса: **`ObservabilityService`**.

Дальнейшая логика (вы пишете код сами или копируете из своей ветки):

- Класс помечаете **`@Service`** (чтобы Spring создал один экземпляр и внедрял через конструктор).
- Внутри — потокобезопасное хранилище: например **список/очередь** пар **(Instant timestamp, String category, long durationNanos)**.
- Публичные методы:
  - **`void record(String category, long durationNanos)`** или удобная обёртка **`ObservationScope`** с **`AutoCloseable`**/`try-with-resources`, чтобы не забыть `stop`.
- Инжектите **`Clock`** (**`Clock.systemUTC()`**) или просто **`System.nanoTime()`** — главное последовательно.
- Из **`application.properties`** читаете три **`Duration`** (см. шаг 4.4).

**scheduled-метод** (назовите например **`logAggregates()`**):

- Аннотация **`@Scheduled(fixedDelayString = "${observability.log-interval}")`** или **`fixedRate`** — интервал между публикациями в лог (**5–10 сек** разумный старт).
- В методе:
  1. Удалить из хранилища записи старше **максимального** из трёх окон (чтобы память не росла).
  2. Для каждого окна (короткое / среднее / длинное) и каждой **категории** посчитать **count**, **sum**, **avg** (мин/макс по желанию).
  3. **`log.info`** одной понятной строкой или несколькими; формат такой, чтобы **потом искать grep-ом в сохранённом файле**.

**Зачем:** это «сердце» отчётности LAB9 без внешнего Grafana.

### Шаг 4.4. Прописать настройки в `application.properties`

1. Откройте **`src/main/resources/application.properties`**.
2. В **конец** файла добавьте блок с префиксом, например:

```properties
# LAB9 Observability — длительности окон (скользящая статистика)
observability.window.short=10s
observability.window.medium=30s
observability.window.long=1m
observability.log-interval=PT5S
```

Имена ключей можете подогнать под свой код (главное — **они читаются** в **`ObservabilityService`** через **`@ConfigurationProperties`** или **`@Value`**).

**Зачем:** параметризация окна без перекомпиляции «магических констант». Методист видит вашу дисциплину конфигурации.

### Шаг 4.5. Внедрить `ObservabilityService` в контроллеры

Для **каждого** класса из пакета **`rental.controller`**:

1. Откройте, например, **`StatsController.java`**.
2. Добавьте **поле** `private final ObservabilityService observabilityService` и параметр конструктора (если уже **`@Autowired` конструктор** — добавьте туда второй параметр).

**Шаблон внутри каждого публичного метода:**

```java
long startNanos = System.nanoTime();
try {
    // … существующая логика метода без изменений смысла …
    return результат;
} finally {
    observabilityService.record(
        "web.StatsController.stats",
        System.nanoTime() - startNanos
    );
}
```

**Зачем:** вы измеряете **именно вход по HTTP**, до и после вашей цепочки.

Повторите для **`RentController`**, **`ClientController`**, **`CarController`**, **`DevController`** (и любых других контроллеров в проекте).

**Не ломайте API:** имена методов, URL mappings, типы возврата **не меняются** — только оборачиваются.

### Шаг 4.6. Тайминги обращений к БД

Сейчас **`StatsController`** дергает репозитории напрямую. По заданию нужны замеры **`db`**-операций. Два понятных пути (выберите один и не смешивайте хаосом):

**Вариант A (прозрачен для отчёта).** Оборачиваете **вызовы `carRepository/clientRepository/rentRepository`** в методе **`stats()`** в отдельные **`record("db.stats.countCars", …)`**, **`record("db.stats.countClients", …)`** и т.д.

**Вариант B.** Переносите агрегирование **`/stats`** в **`StatsService`** и ставите там замеры **на каждый метод репозитория**.

**Зачем:** на графике k6 «всё плохо», а в логах видно «на самом деле три `count()` занимают столько».

Аналогично — добавьте категории **`db`** в ключевые методы **`RentService`**, **`ClientService`**, **`CarService`** там, где внутри реальные транзакции/запросы JPA.

В терминале **из папки `zil`**:

```bash

```

**Зачем:** сломанный конструктор контроллера сразу всплывает.

### 7.2. Запуск **обоих** контейнеров (**`app`** + **`additional`**) на **hl07** с CPU **0.5**

**В том же сеансе shell**, **до** `docker compose`:

```bash
export APP_CPUS=0.5
export ADDITIONAL_CPUS=0.5
docker compose --env-file registry-tags-lab8-hl7.env pull app additional
```

**Зачем:** Compose подставляет `${APP_CPUS}` из окружения (см. **`docker-compose.yml`**). Если забыть `export`, часто возьмётся значение по умолчанию **1.0** и отчёт «про 0.5» будет подделкой.

Проверка с ** hl07**:


## Часть 8. ВМ k6 (**hl11**) — куда смотреть и что набрать

### 8.1. Какой IP подставить в **`BASE_URL`**

- Если **`additional` на hl07** (часть **7.2**): узнайте **внутренний IP hl07** (`hostname -I` на hl07):  
  **`BASE_URL=http://<IP hl07>:8084`**

- Если **`additional` на hl13** (**часть 3А**): узнайте **внутренний IP hl13** и используйте **его**, а не hl07:  
  **`BASE_URL=http://<IP hl13>:8084`**

**Зачем:** k6 бьёт **в порт процесса, который принимает внешний трафик** для `/additional/...`; этот процесс где-то **физически** слушает **8084** — нужно указать именно ту ВМ.

**Как связано с LAB7-маршрутами:** между ВМ нужен допустимый маршрут до адреса вроде **`10.60.*.*`** (см. [LAB7_REPEAT_MANUAL_PGADMIN_SEED_K6_RU.md](LAB7_REPEAT_MANUAL_PGADMIN_SEED_K6_RU.md), раздел про сеть).

### 8.2. Склонировать / обновить `zil` только ради **`k6`**

На **hl11**:

```bash
git clone git@github.com:<org>/Labs_hls.git   # если ещё нет
cd Labs_hls/zil/k6
git checkout lab9
git pull
```

### 8.3. Запуск k6 и сохранение JSON CPU 0.5

```bash
# IP той ВМ, где реально слушает 8084 (hl07 если оба там; если additional на hl13 — IP hl13 — часть 3А):
```

Если хотите смесь GET `/additional/stats` и availability (как в LAB8 для графика availability), задайте **`STATS_SHARE=0.5`** и сохраните в имя **`s2s_cpu05_mix50.json`** — ориентир по именованию см. LAB8 отчёт.

Альтернатива без `scp`: через веб-браузер Git / артефакты CI / вставить JSON в ваш fork — главное сохранить данные без потерь; удобно иметь файлы локально под Python и офлайн-графики.

## Часть 13. Частые ошибки («почему ничего не работает»)

| Симптом | Причина | Что сделать |
|---------|---------|--------------|
| В логах нет ваших строк | Нет **`@EnableScheduling`** или ошибка компонента | поправить аннотации, **`docker compose logs app`** первые строки старта |
| Одно приложение без метрик | Смотришь не тот сервис | читать **и** **`app`** **и** **`additional`** или объединять `logs` |
| k6 **`connection refused`** | Неверный host в **`BASE_URL`** (**8084** на другой ВМ), контейнер down | **`BASE_URL=http://IP_узла_где_additional:8084`** (часто **hl13**, не hl07); **`curl`** до порта с **hl11** |
| **`additional` 500 / timeout к CRUD** | На hl13 указан **`localhost:8083`** или **`http://app:8083`** | **`MAIN_SERVICE_BASE_URL=http://<внутренний_IP_hl07>:8083`** — **часть 3А** |
| CPU не меняется | Забыл **`export APP_CPUS`**, только env-файл | задаётся **переменная окружения** хоста, см. **`docker-compose.yml`** |
| Старый код внутри образа | Тег образа **`lab9`**, а pull тянет кэш | **`--force-recreate`**, проверить **`ZIL_*_IMAGE`**, иногда **`docker compose pull` снова** |
