# LAB5: что сделали и как это устроено (простыми словами)

## Что за лаба по смыслу

**Цель:** научиться **не руками** в Postman плодить сотни записей, а **скриптом** залить в БД много **случайных, но валидных** тестовых данных, чтобы потом (например, в **LAB4 / k6**) гонять нагрузку на **реалистичном** объёме.

По цепочке в жизни обычно так:

1. Подняли **Spring Boot** + **PostgreSQL** (как в LAB3: `docker compose` или `bootRun` + контейнер только с БД).
2. **Очистили** таблицы одной HTTP-командой — **`POST /dev/clear`**. Зачем: чтобы каждый прогон начинался **с пустой базы** (или с предсказуемого состояния), и скрипт заливки не упирался в дубли VIN, телефонов и т.д.
3. Запустили **Python-скрипт** `seed.py` — он через обычный **REST** (`POST /clients`, `POST /cars`, `POST /rents`) создаёт N сущностей. Имена/цвета/текст «по-человечески» даёт **Faker**, числа и UUID — в коде.
4. Дальше можно запускать **k6** (`zil/k6`), чтобы смотреть, как ведёт себя API под нагрузкой.

Итог в репозитории:

| Часть | Файл(ы) | Роль |
|--------|---------|------|
| Очистка БД по HTTP | `DevController.java`, `DevDataService.java`, `ClearTarget.java` | `POST /dev/clear?clear=…` — `all` = все таблицы; **иначе** имя «корневой» сущности: при необходимости сначала снимаются **аренды** (дочерняя таблица по FK), затем выбранные **cars** или **clients**. |
| Заливка данных | `seed.py` | Клиент: дергает API как браузер/Postman, не лезет в SQL напрямую. |

| План/чеклист (кратко) | `LAB5_PLAN.md` | Пошаговый сценарий защиты, Postman, про Flyway V2 — см. там. |
| Защита «простыми словами» + карта кода | `LAB5_DEFENSE_AND_CODE_RU.md` | Речь, порядок демо, разбор `ClearTarget` / `DevDataService` / `seed.py`. |
| Стартовые данные в БД при первом развёртывании | `V2__seed_data.sql` | Flyway при миграции **один раз** вставит демо-строки. Скрипт `seed.py` **перед** заливкой (если не `--no-clear`) вызывает `POST /dev/clear` и **стирает** и их тоже — дальше в таблицах только то, что создал `seed`. |

## Конспект: как связаны таблицы и что значит `clear=…`

В схеме Flyway (и в JPA) три бизнес-таблицы:

- **`clients`** — клиенты, первичный ключ `id`.
- **`cars`** — машины, первичный ключ `id`, уникальный `vin`.
- **`rents`** — аренды: поля `car_id` и `client_id` — **внешние ключи** на `cars.id` и `clients.id`.

Связь по смыслу (кто кого тянет «наверх»):

- Строка в **`rents`** **обязана** указывать на **существующие** `cars` и `clients`.
- Значит **`rents` — дочерняя** таблица; **`cars` и `clients` — родительские** (без взаимной FK друг на друга).

Поэтому:

- Удалить **машину** или **клиента**, пока на них ссылается хотя бы одна **аренда**, PostgreSQL **не даст** (или нужен CASCADE, у нас — явный порядок в коде).
- Сначала всегда убираем **ссылки** (`rents`), потом **то, на что ссылались** (`cars` / `clients`), если выбран режим, где их тоже нужно пустить.

## Параметр `?clear=` — полная выборка или одна «корневая» сущность

**Имя параметра в URL и в CLI: `clear`**, не `target`.

Порядок реализован в `ClearTarget` + `DevDataService.clearByTarget(...)`:

| `?clear=` | Смысл для защиты | Какие таблицы трогаем (по порядку) |
|-----------|------------------|-------------------------------------|
| `all` (по умолчанию, если параметр не писать) | Пустим **всю** бизнес-БД. | `rents` → `cars` → `clients` — безопасно, потому что сначала снимаем все ссылки, потом родителей. |
| `rents` | Очистить **только** «мостик» аренд. | Только `rents`. Машины и клиенты **остаются** — на них никто больше не ссылается в этой схеме, кроме как через `rents` (и мы их удалили). |
| `cars` | Убрать **машины** и всё, что **мешает** их удалить. | Сначала `rents` (они ссылаются на `cars`), потом `clients` **не** трогаем, затем `cars`. |
| `clients` | Убрать **клиентов** и всё, что **мешает** их удалить. | Сначала `rents`, потом `clients`; `cars` **не** трогаем. |

Каждый вызов — **одна транзакция** (`@Transactional` на сервисе).

Неверное значение `clear` → **400 Bad Request** (текст: `clear must be all, rents, cars, or clients, …`).

## Почему нельзя удалять «в любом порядке» (кратко)

То же самое одной фразой: **сначала дочерние строки (`rents`), потом родителей** — иначе нарушение FK в PostgreSQL.

## `POST /dev/clear` — что видит снаружи

- **Метод:** `POST`
- **URL:** `http://localhost:8083/dev/clear?clear=all` (параметр **`clear` можно не указывать** — тогда как `all`). Порт — в `application.properties`.
- **Тело:** не нужно.
- **Успех:** ответ **204 No Content** (нет тела, это нормально).
- **Назначение:** только **учёба / dev**. В **продакшене** такой URL **нельзя** оставлять открытым.

**Примеры:**  
`POST .../dev/clear?clear=rents` — снять только аренды.  
`POST .../dev/clear?clear=cars` — аренды + машины (см. таблицу выше).  
`POST .../dev/clear?clear=clients` — аренды + клиенты.

**Python:** тот же query `clear=`; в командной строке: **`--clear all`** (по умолчанию) или `--clear rents` / `cars` / `clients`.

## `seed.py` — пошагово, что происходит внутри

1. **Разбор аргументов** (`argparse`):
   - `--count` — сколько **основных** записей создать (смысл зависит от `--endpoint`). Не нужен вместе с **`--only-clear`**.
   - `--endpoint` — что заливаем: `clients` | `cars` | `rents`.
   - `--base-url` — куда стучимся (по умолчанию `http://localhost:8083`).
   - **`--clear`** — `all` | `rents` | `cars` | `clients`: уходит в `POST /dev/clear?clear=...` **перед** заливкой (по умолчанию `all` = пустим всё, что описано в таблице выше).
   - `--no-clear` — **не** вызывать очистку перед заливкой.
   - `--only-clear` — только `POST /dev/clear` с выбранным `--clear` и **выйти** (без заливки).

2. **Случайность Faker:**  
   `Faker("ru_RU")` + `Faker.seed(42)` — имена/компании будут **по-русски и стабильно** при одном и том же seed (удобно для повторяемых демо).

3. **Очистка (по умолчанию):**  
   `POST /dev/clear?clear=<значение --clear>` — затем заливка (если не `--no-clear` и не `--only-clear`).

4. **Режим `clients`:**  
   В цикле `count` раз: собрать JSON (имя, права, телефон), **`POST /clients`**.  
   Телефоны специально делают уникальными шаблоном `+79...`, чтобы не ловить уникальные ограничения в БД.

5. **Режим `cars`:**  
   Аналогично: VIN, модель из слов Faker, цена, город из списка, **`POST /cars`**.  
   VIN укорачивается до 17 символов — как ожидает учебный API.

6. **Режим `rents` (самый важный для «зависимых таблиц»):**  
   - Сначала создаётся `count` **клиентов** и `count` **машин** — id **читаются из ответа** JSON и складываются в списки.  
   - Потом `count` раз: случайно выбрать `carId` и `clientId` из списков, проставить **корректные** `startDate` / `endDate` (конец **после** начала), посчитать `totalCost`, **`POST /rents`**.  
   Так вы выполняете требование «сценарий для зависимой сущности» без сырых SQL.

7. **Ошибки HTTP:**  
   Если ответ не 200/201 (или clear не 200/204), скрипт пишет в stderr тело ответа и **выходит с кодом 1** — удобно в CI или в `.ps1` обвязке.

## Связь с k6 (LAB4)

После `seed.py` в базе много **живых** id. Сценарий k6 (например `load.js`) бьёт в **`/cars`**, **`/stats`**, **POST** создания сущностей с долей из env — **нагрузка** уже не на три строки из демо, а на N записей, которые вы залили.

Практичный порядок:

`docker compose up` (или БД + `bootRun`) → `python seed.py ...` → `k6 run ...`.

## Где в коде Spring регистрируется `/dev/clear`

- `DevController` — обычный `@RestController`, Spring сам поднимает бин, если компонент сканируется из пакета приложения.  
- `DevDataService` — `@Service` с **тремя репозиториями** JPA.  
- Репозитории — `JpaRepository` из LAB2/3, метод `deleteAll()` — стандарт Spring Data.

Интеграционные тесты режимов очистки: `src/test/java/rental/controller/DevControllerTest.java`. Дополнительно полезна **ручная** проверка в Postman/curl.

## Быстрые команды (Windows, из папки `zil`)

Создать venv (один раз):

```powershell
python -m venv .venv
.\.venv\Scripts\pip install -r requirements.txt
```

Очистка + 10 клиентов:

```powershell
.\.venv\Scripts\python.exe seed.py --count 10 --endpoint clients
```

Только дозалить, не трогая текущие данные:

```powershell
.\.venv\Scripts\python.exe seed.py --no-clear --count 5 --endpoint cars
```

Только стереть аренды, оставив машины и клиентов:

```powershell
.\.venv\Scripts\python.exe seed.py --only-clear --clear rents
```
